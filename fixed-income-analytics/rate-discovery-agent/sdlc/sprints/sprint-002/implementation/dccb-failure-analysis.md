## Headline

**Sprint 001 cloud (n=350)** → **Sprint 002 local diagnostic (n=34)**:

| | Cloud | Local | Lift |
|---|---:|---:|---:|
| `success` rate | 4.9% | **55.9%** | **+51 pp / 11.4×** |
| `partial_success` rate | 32.9% | 17.6% | -15.3 pp |
| `discovery_failed` rate | 61.1% | 8.8% | -52.3 pp |
| Avg cost / bank | $0.157 | $0.105 | -33% |
| Avg tool calls / attempt | 10.4 | 5.6 | -46% |

Even more striking: **`candidates_all_failed` banks** (cloud said every fetch errored, no website exists) **gave 58% success rate locally.** And the `reachable_uncommitted` cohort (cloud fetched but couldn't commit) gave 53%. The "no web presence" framing from the cloud run was wrong for most of the failed cohort.

## Method

1. **Sample.** 34-bank stratified selection across v2 phase_outcomes cohorts and India macro-regions. Generated by `scripts/analysis/select-dccb-diagnostic-sample.js`. Distribution: 15 `reachable_uncommitted`, 12 `candidates_all_failed`, 3 `found_committed_manual`, 3 `found_committed`, 1 `no_candidates`.

2. **Execution.** `scripts/run-dccb-diagnostic.js` ran `node run-discovery.js` per bank with `--log-level debug`, all output into `output/runs/2026-05-11T1732_sprint002-diagnostic/`. Local AOAI endpoint, same Tier 1 (gpt-4.1-mini) + Tier 2 (gpt-4.1) routing as the cloud run. Search via AOAI Responses API (same as cloud — no Bing key set).

3. **What changed in the agent path between Sprint 001 and Sprint 002:**
   - **#6 slug consistency:** canonical `bank_code` injected into the prompt, `slugify` tool registered, server-side slug-guard catches rogue product-variant files. Slug-guard activity this run: **0 rogue files, 0 corrections** — the prompt + tool prevented all drift.
   - **#2 v2 classification:** every per-bank summary now carries `phase_outcomes` triple + tier-2 `failure_class` (this is the lens the analysis uses, not a behavior change).
   - **Prompts tightened:** explicit forbidden-suffix list, single-canonical-slug rule.
   - No agent-side change to the core discovery flow. The agent's strategy is unchanged; only the slug/identity layer and the classification post-processing changed.

## Findings

### Cohort-by-cohort lift

| Source cohort (cloud) | N | success | partial | disc_failed | extr_failed | no_rates |
|---|---:|---:|---:|---:|---:|---:|
| `reachable_uncommitted` | 15 | **8 (53%)** | 4 | 2 | 1 | 0 |
| `candidates_all_failed` | 12 | **7 (58%)** | 2 | 1 | 1 | 1 |
| `found_committed_manual` | 3 | **2 (67%)** | 0 | 0 | 0 | 1 |
| `found_committed` | 3 | **2 (67%)** | 0 | 0 | 1 | 0 |
| `no_candidates` | 1 | 0 | 0 | 0 | 1 | 0 |
| **TOTAL** | **34** | **19 (56%)** | **6 (18%)** | **3 (9%)** | **4 (12%)** | **2 (6%)** |

Per-cohort reads:

- **`reachable_uncommitted` (15 banks): 53% now succeed.** Cloud rejected these as "couldn't commit a website" — but locally most found the right site and extracted rates cleanly. The 4 partials are also wins (website found, rate page not). Only 2 discovery failures and 1 extraction failure remain.

- **`candidates_all_failed` (12 banks): 58% now succeed.** This is the biggest surprise. Cloud said every fetch errored — locally these banks found and committed to a website on the first or second attempt. Strongly suggests the cloud bottleneck was environmental (network path, AOAI Responses-API behavior in cloud, or tool-budget pressure), not "the banks don't have websites."

- **`found_committed_manual` (3 banks, all West Bengal): 2 succeeded.** The third (`bankura`) classified as `no_rates_expected` because the agent's notes mentioned "no fixed deposit"-style language. Worth manual operator verification — could be a real classifier hit (bankura genuinely doesn't offer FDs) or a false positive of the regex.

- **`found_committed` (3 controls): 2 reproduced as `success`, 1 became `extraction_failed`.** The regression case is `banswara-central` — had 45 slabs in cloud, has 0 locally. Investigation below.

- **`no_candidates` (1 bank): `extraction_failed`.** `nizamabad-district-co-operative-central-bank-ltd` had no fetch attempts in cloud; locally the agent committed to `nizamabaddccb.bank.in` (an `html_js` page) but extraction failed. Suggests Tier 2 was invoked for a JS-heavy page and still couldn't extract — Playwright fallback may not have fired.

### The slug-ghost cohort — what happened

Three banks in the sample (`barmer-central`, `chittoor`, `chikmagalur`) had non-zero slabs in the cloud run despite missing config files (slug-ghost suspects). Their local outcomes:

| Bank | Cloud (slabs) | Local | Read |
|---|---:|---|---|
| `barmer-central-co-operative-bank-ltd` | 45 | `extraction_failed` (0 slabs) | The 45 cloud slabs were likely from a misextraction off a portal page that the agent now correctly rejects. Net data quality improvement. |
| `chittoor-district-co-operative-central-bank-ltd` | 9 | `success` (9 slabs) | Reproduced cleanly with config. Slug-ghost wasn't a misextraction — it was just a writer bug. |
| `chikmagalur-district-central-co-operative-bank-ltd` | 7 | `success` (10 slabs) | Reproduced and improved. Slug-ghost wasn't a misextraction here either. |

`banswara-central` (45 cloud slabs, was `found_committed`, became `extraction_failed` locally) is the most suspicious — possibly the same "cloud over-extracted from a wrong page" pattern. Operator should spot-check whether banswara.bank.in actually has 45 rate slabs or whether the cloud number was from a sibling state-coop page.

### Slug-guard activity

Zero. No banks produced rogue product-variant files (`_current_rates.json` etc.), no banks needed `bank_code` corrections. The combination of `$BANK_CODE` prompt injection + `slugify` tool + tightened prompt was sufficient. The slug-guard runs as belt-and-suspenders insurance; the diagnostic confirms it currently has nothing to do.

### Tool-call efficiency

| Metric | Cloud | Local |
|---|---:|---:|
| Avg tool calls per final summary | 10.4 | 5.6 |
| Banks needing Tier 2 retry | 339/350 (97%) | 20/34 (59%) |
| Avg cost per bank | $0.157 | $0.105 |

Tier 1 success rate jumped from 3% (cloud) to 41% (local). With more banks resolved at Tier 1, the system burns far fewer tool calls and far less money.

### What's left after this run

7 banks not in `success` / `no_rates_expected`:
- 6 `partial_success` — operator-actionable. Each has a website committed but no rate page found. Visiting each and capturing the FD page URL would convert them to `success` on the next run.
- 4 `extraction_failed` — page found but no slabs. Likely an extraction-prompt issue or a JS-heavy page that needs Playwright.
- 3 `discovery_failed` — genuinely look like no web presence after local effort.
- 2 `no_rates_expected` — flagged by the notes regex; spot-check whether it's a real positive.

The 6 `partial_success` cohort is the most directly actionable in Sprint 002 — an operator can convert them to `success` in minutes with manual rate-URL capture.

## Implications for Sprint 002 item #5 (codify learnings)

The diagnostic shifts what item #5 should prioritize. Pre-running, my expectation (and the v2 taxonomy doc) was that the largest leverage point would be "pre-classify DCCBs as no-website-known in `bank-domains.json`." The data flips that.

**Item #5 high-priority actions:**

1. **Don't pre-classify DCCBs as no-website by default.** The Sprint 001 cloud baseline's 61% `discovery_failed` rate over-counted. Local replication brought it to 9%. The right move is to RE-RUN the failed cohort locally before declaring banks as no-website. A "no_website_known" registration should require **two failed local runs** (not just one), or operator confirmation.

2. **Investigate the cloud-vs-local gap.** A 11× lift in success rate is too large to be agent improvements alone (and item #6 alone almost certainly didn't account for it — slug-guard caught nothing). Hypotheses:
   - Cloud's AOAI Responses API search behaves differently from local invocation. Possible — Responses-API tool grounding can vary by host.
   - Container Apps networking interferes with some bank-site fetches (regional IP geo, TLS, headers).
   - Cloud's tool-call budget pressure caused premature give-ups.
   The fastest way to isolate: run the SAME 34 banks in cloud (with #8/#9/#10 fixes applied) and compare to local. **This should precede #12 (full DCCB rerun).** Otherwise we'll declare a cloud-DCCB-lift that's actually a local-vs-cloud-environmental-gap.

3. **Operator follow-up for the 6 `partial_success` banks.** Visit each, capture the FD rate URL, update `bank-domains.json`. Next local run converts them to `success` deterministically. Bank list:
   - `agra-zilla-sahakari-bank-ltd` (UP) — found_committed website, rate page not found
   - `azamgarh-district-central-co-operative-bank-ltd` (UP)
   - `bhatinda-central-co-operative-bank-ltd` (Punjab)
   - `dhanbad-district-central-co-operative-bank-ltd` (Jharkhand) — reachable_uncommitted; agent fetched but didn't commit
   - `gondia-district-central-co-operative-bank-ltd` (Maharashtra)
   - `indore-premier-co-operative-bank-ltd` (MP) — reachable_uncommitted

4. **Investigate the 4 `extraction_failed` banks.** All four committed a website AND a rate page URL, but extraction yielded 0 slabs:
   - `angul-united-central-co-operative-bank-ltd` (Odisha)
   - `banswara-central-co-operative-bank-ltd` (Rajasthan) — was a 45-slab cloud "success"; possible cloud misextraction
   - `barmer-central-co-operative-bank-ltd` (Rajasthan) — same shape as banswara
   - `nizamabad-district-co-operative-central-bank-ltd` (AP) — html_js page; Playwright may not have fired
   The first three rate URLs should be operator-inspected: does the page actually have a rate table the agent missed, or is the URL a directory page?

5. **Skip "pre-classify dead-portal cohorts" for now.** This was the originally-anticipated big lever (block-list `upcooperativebank.org`, `tn.gov.in`, etc.). The diagnostic data doesn't support it — local runs sidestepped the dead portals without a block-list. Re-evaluate only if the cloud re-run shows the dead-portal pattern persists.

## Caveats

- **Sample size.** 34 banks across 6 macro regions. The cohort-relative lift is the trustworthy comparison; absolute numbers may not project to the full 350. The full cloud rerun (#12, after a cloud-only validation of the 34) will validate.
- **Sample isn't random.** Stratified by cloud-run cohort, intentionally over-sampling the "stuck" cohorts. Aggregate rates ARE NOT extrapolation-safe to the full 350. Cohort-conditional rates are.
- **Local vs cloud isn't a single-variable change.** Network paths differ, AOAI Responses-API search may behave differently when invoked from a Container Apps Job vs a developer laptop, the agent's tool-budget headroom may differ. **The cohort-relative lift is the trustworthy comparison; the absolute 11× number depends on isolating the environmental gap.**
- **Slug-fix attribution is weak.** Slug-guard didn't trigger this run, so #6's contribution is **not the driver** of the lift. The lift comes from somewhere else — environment, prompt-tightening, or both. Item #5 should isolate this.
