## What Was Built

### Authentication System

The auth system uses session tokens stored in D1. No third-party auth provider — the entire flow is self-contained within the Hono API on Cloudflare Workers.

**Password hashing** (`packages/api/src/lib/password.ts`, 56 lines):
- Uses PBKDF2 via the Web Crypto API (available in both Cloudflare Workers and Node 20+)
- Parameters: SHA-256 hash, 100,000 iterations, 16-byte random salt
- Storage format: `{saltHex}:{hashHex}` — a single text column in the DB
- `hashPassword(password)` → generates salt, derives 256-bit key, returns hex string
- `verifyPassword(password, stored)` → splits stored value, re-derives with same salt, compares hex output
- Why PBKDF2 and not bcrypt: Cloudflare Workers doesn't support Node's native `crypto` module or `bcrypt`. Web Crypto API is the only option, and PBKDF2 with SHA-256 at 100k iterations provides equivalent security for this use case.

**Database tables** (`packages/api/src/db/schema.ts`):

`users` table:
- `id` (integer PK, autoincrement)
- `email` (text, NOT NULL, unique index) — login identifier
- `name` (text, nullable) — display name
- `password_hash` (text, NOT NULL) — PBKDF2 output in `salt:hash` format
- `role` (text, NOT NULL, default `"user"`) — either `"user"` or `"admin"`
- `created_at`, `updated_at` (ISO timestamps)

`sessions` table:
- `id` (integer PK, autoincrement)
- `user_id` (integer, FK → users.id)
- `token` (text, NOT NULL, unique index) — 64-character hex string from 32 random bytes
- `expires_at` (text, NOT NULL) — ISO timestamp, 30 days from creation
- `created_at` (ISO timestamp)

Migration: `0002_condemned_moon_knight.sql` (auto-generated by drizzle-kit).

**Auth API routes** (`packages/api/src/routes/auth.ts`, 116 lines):

| Endpoint | Auth | Purpose |
|----------|------|---------|
| `POST /api/auth/register` | Public | Create account. Validates email uniqueness, password ≥ 8 chars. Hashes password, inserts user with `role: "user"`, creates session. Returns `{ token, user }` with status 201. |
| `POST /api/auth/login` | Public | Authenticate. Looks up user by email, verifies password against stored hash. Creates new session (30-day TTL). Returns `{ token, user }`. Returns 401 if credentials invalid. |
| `POST /api/auth/logout` | Required | Invalidate session. Deletes the session row matching the Bearer token. |
| `GET /api/auth/me` | Required | Return current user. Used by the frontend on page load to check if an existing token is still valid. Returns `{ user: { id, email, name, role } }`. |

Token generation: `crypto.getRandomValues(new Uint8Array(32))` → hex string. This produces 256 bits of entropy, sufficient for session tokens.

**Auth middleware** (`packages/api/src/middleware/auth.ts`, 88 lines):

Two middleware functions, both created with Hono's `createMiddleware`:

`requireAuth`:
1. Reads `Authorization: Bearer <token>` from request header
2. Queries `sessions` table for a matching token that hasn't expired (`expires_at > now`)
3. Queries `users` table for the session's `user_id`
4. Sets `c.var.user` (Hono context variable) with `{ id, email, name, role }`
5. Returns 401 JSON if any step fails

`requireAdmin`:
1. Reads `c.var.user` (set by `requireAuth`)
2. Returns 403 JSON if `user.role !== "admin"`

The middleware extends Hono's `ContextVariableMap` TypeScript interface so that `c.get("user")` is type-safe throughout all route handlers.

### Route Protection

**How it works** (`packages/api/src/app.ts`, 92 lines):

The app creates three Hono sub-apps with different middleware stacks:

```
Public (no middleware):
  /api/health
  /api/auth/register, /api/auth/login
  /api/rates/best  ← homepage data, always accessible

Authenticated (requireAuth):
  /api/banks, /api/banks/:code
  /api/rates, /api/rates/compare, /api/rate-changes
  /api/banks/:code/rates

Admin (requireAuth + requireAdmin):
  /api/admin/discovery-stats
  /api/admin/flags, /api/admin/flags/:id
  /api/admin/scrape-runs
  /api/admin/pipeline-health
```

The `/api/rates/best` endpoint is duplicated as an inline handler in app.ts (rather than going through the authenticated `rateRoutes`) because it must remain public for the homepage. All other rate endpoints require login.

**Why sub-app grouping instead of `app.use()` path patterns**: Hono's `app.use("/api/banks/*", ...)` only matches paths with at least one character after the prefix — it doesn't match `/api/banks` itself. Using sub-apps (`const authed = new Hono(); authed.use("*", requireAuth); authed.route("/", bankRoutes)`) applies middleware to all routes in the group regardless of path structure.

### Frontend Auth

**Auth context** (`packages/web/src/context/auth.tsx`, 116 lines):

React context providing `{ user, token, loading, login, register, logout }` to the entire app. Wrapped around `<Outlet />` in the root layout.

Session persistence: token stored in `localStorage` under key `"bird_token"`. On app load, the context reads the stored token and calls `GET /api/auth/me` to validate it. If the token is expired or invalid, it's cleared from localStorage and the user is treated as logged out.

`login(email, password)` and `register(email, password, name)` return `null` on success (token stored, user set) or an error message string on failure. The calling component displays the error.

`logout()` calls `POST /api/auth/logout` as fire-and-forget (the session is invalidated server-side) and immediately clears localStorage and context state.

**API client token attachment** (`packages/web/src/lib/api.ts`):

The shared `request()` function reads the token from localStorage and attaches it as `Authorization: Bearer <token>` to every API call. If the response is 401, the token is cleared from localStorage so the auth context picks up the change on the next render.

This means every API call from any page automatically includes auth without the page needing to know about tokens.

**Route guards** (`packages/web/src/routes/__root.tsx`):

`AuthGate` component wraps the `<Outlet />`:
- If loading (checking stored token): shows "Loading..."
- If not authenticated and path is not in `PUBLIC_PATHS` (`/`, `/login`, `/register`): redirects to `/login`
- If path starts with `/admin` and `user.role !== "admin"`: shows "Access Denied" message
- Otherwise: renders the child route

The homepage (`/`) is always accessible. It shows best rates publicly and a "Sign in" CTA for full access.

**Login page** (`packages/web/src/routes/login.tsx`, 91 lines):
- Email + password form with error display
- Redirects to `/` if already authenticated
- On success: navigates to `/`

**Register page** (`packages/web/src/routes/register.tsx`, 101 lines):
- Name + email + password form (password minimum 8 characters)
- Redirects to `/` if already authenticated
- On success: auto-logs in (register returns a session token) and navigates to `/`

### Mobile Navigation

The root layout header (`__root.tsx`) now has two nav modes:

**Desktop (≥ 768px)**: horizontal link row, same as before but role-aware. Admin links (Pipeline, Flags, Discovery) only render when `user.role === "admin"`. A vertical separator divides consumer links from admin links. User email and logout button shown on the right.

**Mobile (< 768px)**: hamburger icon (three horizontal lines, switches to X when open). Tapping it toggles a slide-down panel containing the same links in a vertical stack. The panel auto-closes when any link is clicked (via `onClick={() => setMenuOpen(false)}` on the container).

The hamburger icon is an inline SVG (no icon library dependency) that morphs between the menu and close icons based on state.

### Admin User Seeding

**CLI tool** (`packages/scraper/src/cli/seed-admin.ts`, 83 lines):

```bash
npm run -w @bird/scraper seed-admin -- --email admin@bird.app --password secret123 [--name Admin]
```

Creates an admin user directly in the local D1 database. If the email already exists, updates the user's role to admin and resets the password. Uses the same PBKDF2 hashing as the API (Web Crypto API is available in Node 20+).

This is the only way to create the first admin user. Subsequent users can be promoted to admin by updating the `role` column directly in the database.

### Trust Tier Correction

The trust tier function went through three iterations during Phase 4:

**Version 1** (Phase 3, original): `getTrustTier(depositInsurance, category, scrapedAt)` — factored in data freshness. A PSB with stale data (>30 days) would show "Verify Safety". This was wrong because the safety of a PSB doesn't change when our data gets old.

**Version 2** (first fix): when `scrapedAt` was not provided (banks list page has no rate data), the function returned "Verify Safety" for all insured banks because `daysSince(undefined)` returned `Infinity`.

**Version 3** (final): `getTrustTier(depositInsurance, category)` — freshness removed entirely. The logic is now:
- Not insured → `"low"` ("Verify Safety")
- Insured + PSB/PVB/SFB → `"high"` ("High Safety")
- Insured + other categories → `"medium"` ("Insured")

Data freshness is shown as a separate indicator on pages that have `scraped_at` data (bank profile, FD rates table) but does not affect the safety tier. This is the correct design: institutional safety is a property of the bank's regulatory status, not of our data pipeline's last run time.

### UI Polish

**Loading skeletons** (`packages/web/src/components/skeleton.tsx`, 57 lines):

Three reusable components:
- `Skeleton` — base component: a `div` with `animate-pulse rounded bg-muted` and custom width/height via className
- `TableSkeleton` — renders a table skeleton with configurable rows and columns. Header cells are short (w-20), body cells alternate between wide (w-40 for first column) and narrow (w-16 for data columns)
- `CardGridSkeleton` — a 2×2 or 4-column grid of card skeletons, each with three shimmer lines

Applied to all 9 data-loading pages: homepage, FD rates, bank profile, compare, rate changes, banks list, admin pipeline, admin flags, admin discovery.

**Compare tenure alignment** (`packages/web/src/routes/compare.tsx`):

The original compare page used exact tenure key matching (`${tenure_min_days}-${tenure_max_days}`). When two banks parse "21 months" as 637 vs 639 days, they appeared as separate rows — one with Bank A's rate and a dash for Bank B, and vice versa.

Fix: `findMatchingTenure(minDays, maxDays)` searches existing tenure rows for a match within ±5 day tolerance on both min and max. If found, the rate is assigned to the existing row. If not, a new row is created. This collapses near-identical tenures into a single comparison row. The tolerance of 5 days handles the common case of month-to-day conversion differences (30 vs 31 days per month).

**FD Calculator auto-fill** (`packages/web/src/routes/calculators/fd.tsx`):

The calculator now reads URL search params on load: `?rate=6.50&years=1&months=6&bank=HDFC+Bank`. The `useState` initializers use lazy functions that check for search params:

```typescript
const [rate, setRate] = useState(() => search.rate ? Number(search.rate) : 7.0);
```

When `bank` is present, the calculator shows "Calculating for HDFC Bank at 6.50% for 1y 6m" above the form. Without params, it shows the generic description.

The bank profile page adds a "Calculate maturity" button to every rate slab row, linking to the calculator with pre-filled rate, tenure (converted from days to years + months), and bank name.

**Empty states**:

Every page that can show no data now has a styled panel with an explanation and actionable guidance:

| Page | Empty Message | Action |
|------|--------------|--------|
| Homepage (no rates for tenure) | "No rates found for X tenure" | "Try a different tenure period above" |
| FD Rates (filters too narrow) | "No rates match your filters" | "Try broadening tenure range or removing DICGC-only filter" |
| Bank Profile (no rates) | "No rate data available for this bank" | "Visit bank website" link if URL available |
| Compare (< 2 banks) | "Select at least 2 banks" | Suggested comparisons: "SBI vs HDFC vs Kotak" |
| Rate Changes (empty) | "No rate changes detected yet" | Explains when changes appear |
| Banks List (empty search) | "No banks found" | "Try a different search term or clear filters" |
| Admin Flags (queue empty) | "No unresolved flags" | "New flags appear after pipeline imports" |

## Discovery Page Auth Fix

The admin discovery page (`/admin/discovery`) was using raw `fetch()` instead of the shared API client, so it didn't attach the auth token after Phase 4's route protection was added. The API returned 401, which the component parsed as a valid `DiscoveryStats` object. Accessing `stats.by_discovery_status.discovered` on the error response `{error: "Authentication required"}` threw "Cannot read properties of undefined".

Fix: added `Authorization: Bearer <token>` header from localStorage, plus error handling on the fetch response.

### Deployment Steps

1. `wrangler d1 create bird-db` — created remote D1 database
2. Updated `wrangler.jsonc` with real database ID and production env (CORS origins, environment vars)
3. `wrangler d1 migrations apply bird-db --remote` — applied all 3 migrations
4. `wrangler d1 execute bird-db --remote --file=seed.sql` — seeded 1958 banks
5. Generated `data-export.sql` from local DB — **using bank codes (not IDs)** because autoincrement IDs differ between local and remote
6. `wrangler d1 execute bird-db --remote --file=data-export.sql` — loaded products, rate slabs, special schemes, bank updates, admin user
7. `wrangler d1 execute bird-db --remote --file=data-export-extra.sql` — loaded scrape_runs, scrape_flags, rate_change_log (missed in first export)
8. `wrangler deploy --env production` — deployed API Worker
9. `wrangler pages project create bird-web` — created Pages project
10. `wrangler pages deploy packages/web/dist` — deployed frontend

### Data Export Challenge

The local D1 database (seeded via Wrangler) assigns autoincrement IDs starting from 1959 (due to prior seed runs), while the remote DB starts from 1. All foreign key references in the export SQL had to use subqueries by bank code instead of hardcoded IDs:

```sql
-- Wrong: hardcoded local ID
INSERT INTO products (bank_id, ...) VALUES (1959, ...);

-- Correct: resolve by code
INSERT INTO products (bank_id, ...) VALUES ((SELECT id FROM banks WHERE code = 'state-bank-of-india'), ...);
```

The export scripts (`data-export.sql` and `data-export-extra.sql`) use this pattern for all FK references.

### Production Bugs Found and Fixed

**1. Auth context hardcoded `/api` path** — The `AuthProvider` in `context/auth.tsx` used `fetch('/api/auth/login')` which in production hits the Pages static server (returning HTML), not the Workers API. The browser couldn't parse the HTML as JSON, producing "Failed to execute 'json' on 'Response': Unexpected end of JSON input". Fix: use `VITE_API_URL` env var, same as `api.ts`.

**2. CORS wildcard subdomains** — Cloudflare Pages generates unique hash URLs per deployment (`b57a1456.bird-web.pages.dev`). The CORS origin list only had `bird-web.pages.dev` and `master.bird-web.pages.dev`, so preview deployments were blocked. Fix: added wildcard support (`https://*.bird-web.pages.dev`) with a suffix-matching function in the CORS middleware.

**3. Discovery page hardcoded `/api`** — Same issue as #1 but in the admin discovery page, which used raw `fetch()` instead of the shared API client. Fix: use `VITE_API_URL`.

**4. Logout hardcoded `/api`** — The logout call in `auth.tsx` used `fetch('/api/auth/logout')`. Fix: use `API_BASE`.

**5. Missing remote data** — The initial `data-export.sql` only included bank updates, users, products, rate_slabs, and special_schemes. It omitted `scrape_runs` (86 rows), `scrape_flags` (282 rows), and `rate_change_log` (32 rows). Without these, the Pipeline dashboard showed empty metrics, the Flags review queue was empty, and the Rate Changes feed had nothing. Fix: generated `data-export-extra.sql` with the missing tables.

**6. Web build script** — `package.json` had `"build": "tsc -b && vite build"`. The `tsc -b` fails because `tsconfig.json` references sub-configs with `noEmit: true` (incompatible with composite mode). This is a pre-existing Phase 0 issue. Fix: changed to `"build": "vite build"` — Vite handles TypeScript via SWC, making `tsc -b` redundant for the build.

### Lesson: Hardcoded Base URLs

The most pervasive production bug was hardcoded `/api` paths scattered across components. In development, the Vite proxy transparently forwards `/api/*` to `localhost:8787`. In production, there's no proxy — the frontend and API are on different origins. Every `fetch()` call must use the configurable `VITE_API_URL`.

Files affected: `api.ts` (fixed in Phase 4 initial), `context/auth.tsx` (2 occurrences), `admin/discovery.tsx`. The pattern going forward: **never use raw `fetch('/api/...')`** — always go through the shared `api.ts` client or read `import.meta.env.VITE_API_URL`.

## Deviations from Plan

- **No OAuth / Cloudflare Access**: Plan mentioned OAuth (Google) as an option. Implemented email/password only for simplicity. OAuth can be added later as an additional login method.
- **Public `/api/rates/best` implemented as inline handler**: Plan didn't specify how to exempt specific endpoints from auth. The cleanest Hono approach was duplicating the handler in app.ts outside the authenticated sub-app. The alternative (a whitelist in the middleware) would couple the middleware to route knowledge.
- **`seed-admin` duplicates password hashing logic**: The API's `password.ts` runs in Cloudflare Workers. The CLI's `seed-admin.ts` runs in Node.js. Both use Web Crypto API (available in both runtimes), but the code is duplicated because the API package uses Wrangler-specific imports that can't be loaded in Node. If the hashing algorithm changes, both must be updated.
- **Session cleanup not implemented**: Expired sessions accumulate in the database. A periodic cleanup job (delete sessions where `expires_at < now`) should be added to the pipeline script.
- **Deployment not in original Phase 4 plan**: The plan focused on auth, RBAC, and polish. Deployment was added opportunistically since the auth work required production testing to surface real issues (CORS, base URLs, data export).

## Known Issues / Debt

1. **No password reset flow** — users who forget their password have no recovery path. Requires email sending capability.
2. **Expired sessions not cleaned up** — `sessions` table grows indefinitely. Need a periodic DELETE.
3. **Token in localStorage** — vulnerable to XSS. httpOnly cookies would be more secure but require CORS cookie configuration for the Cloudflare Workers API.
4. **Register is open** — anyone can create an account. If the intent is invite-only, registration should be disabled or require an invite code.
5. **Admin promotion only via CLI** — no web UI to manage user roles. An admin user management page could be added.
6. **Mobile nav doesn't close on outside click** — only closes when a link inside is clicked. Should also close when clicking outside the menu area.
7. **No rate limiting on auth endpoints** — `/api/auth/login` and `/api/auth/register` have no rate limiting, making them vulnerable to brute force. Cloudflare's built-in rate limiting or a middleware counter would help.
8. **Data export is manual** — no automated script to sync local DB changes to remote. The `data-export.sql` and `data-export-extra.sql` are one-time artifacts. Future pipeline runs need a proper sync mechanism.
9. **Non-production Worker also deployed** — `wrangler deploy` (without `--env production`) created a `bird-api` Worker with development vars. Should be deleted or repurposed as staging.
